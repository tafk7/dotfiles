**Review of `issues/setup-update-redesign.md`**

Reviewed on 2026-10-25 against checkout `352b71e0bf018cf386d91c463b9b3d254fb3ebef` and the untracked proposal present in the workspace. Line numbers below refer to that checkout and proposal. This was a static, read-only code review; setup, installers, tests, and live tmux mutations were not run. The only requested write is this review file. Historical claims about the author's live machine are distinguished from behavior established by the code.

The proposal identifies real problems, and most cited locations are accurate. It needs changes before implementation: preserving recovery information, representing selection correctly, defining ownership and version identity, separating convergence from health, and making refresh state persistent. Phase 1 currently promises capabilities that do not arrive until later phases.

1. **[P1] Do not clear a failed transaction merely to unblock later installs.** Proposal lines 151–152 and 358 describe retained journals as a robustness defect and propose closing them on failure. Retention is an intentional recovery contract. In `lib/install.sh:246-254`, replacement can succeed before the ledger write fails. Clearing the journal then loses the evidence needed to reconcile the active artifact. Tree replacement also has failures after moving the old tree, changing the launcher, or attempting rollback (`lib/install.sh:268-294`).

   Existing tests explicitly require journal retention after replacement and ledger failures (`tests/transaction-failures.sh:24-33`, `:49-63`). The safe rule is: attempt bounded reconciliation or rollback; clear only after the resulting state has been validated and recorded; otherwise retain the journal and block affected mutations. Continuing after a resolved failure is useful. Unconditionally clearing unresolved recovery state is a regression. The plan also omits a fix for its own errexit finding; retaining the conditional phase structure requires auditing every fallible operation for an explicit status check.

2. **[P1] The proposed registry loop would broaden per-tool AI selections, and table order is not an existing dependency contract.** Proposal lines 117–118 call `component_selected` the real selection function. It is unused by installation, but it is also wrong for individual AI flags: `setup.sh:224-229` selects every tool with the `ai` capability whenever any AI tool is requested. `install_ai_selection` separately honors `SELECTED_AI_TOOLS` (`setup.sh:233-240`). The checked-in snapshot already demonstrates `--claude` selecting `claude codex opencode pi` through the predicate while installation invokes only Claude (`tests/fixtures/setup-selection.snapshot:435-446`). Adopting that predicate directly would install unwanted CLIs and potentially introduce an unexpected Node requirement.

   The registry parser stores associative arrays and discards its source table (`lib/registry.sh:172-231`); tier/capability iterators sort names (`:239-259`). Even literal table order puts eget after several tools that need it (`:44-61`). Docker before sbx is only one dependency. Preserve an ordered list or declare dependencies explicitly, including eget bootstrap, apt build dependencies before tmux, package installation before xrdp configuration, and Node availability before Pi. Specify whether `--only` includes prerequisites or reports them as blockers. Preserve the rule that requesting Pi alone does not silently install the work toolchain (`installers/install-pi.sh:55-72`).

3. **[P1] The machine profile needs selection and migration semantics before it can safely drive updates.** Proposal lines 204–210 leave replacement versus merge unspecified. After a full install, does `setup.sh --claude` replace the profile with config+Claude, or add Claude to the saved tier? Does routine `setup.sh --config` reset it to config? Today's config action reconciles installed tools rather than declaring the desired package selection (`setup.sh:96-99`). A profile implementation must not silently forget the machine's previous selection.

   Persist individual AI selections as well as `ai=all`; define whether the latter automatically includes future registry additions. Preserve durable opt-outs such as `--no-git` and `--no-hooks`, otherwise ordinary update/refresh will perform previously excluded operations (`setup.sh:154-160`, `:543-550`, `:579-584`). Include or explicitly exclude settings such as `RDP_XSESSION` (`installers/install-xrdp.sh:28-39`). Avoid making feature preferences in the profile compete with `preferences.tsv` and `dotfiles-feature`.

   The ledger cannot recover intent reliably: reconciliation records discovered external tools and not-applicable components even when they were never selected (`lib/install.sh:120-135`). It also contains partial failures and historical outcomes. Use ledger-based migration as a proposed selection requiring review, not as authoritative intent. Define schema validation, atomic writes, failed-run behavior, and what happens when selections are removed; deselection should not accidentally become uninstall or config retirement.

4. **[P1] `--check` conflates independent states and cannot yet support the promised planner.** Proposal lines 230–234 allow only `current`, `missing`, `outdated HAVE WANT`, and `foreign`. An owned executable can be present but broken, current but missing a companion, pinned but not runnable, unsupported, or blocked by a missing runtime. Ownership and version drift can both apply. A command failure or unreadable state must remain distinguishable from a legitimate result. Downgrades also make “outdated” an awkward description of exact-pin drift.

   Preserve the registry's existing distinctions between command presence, runnable launchers, files, companions, and services (`lib/registry.sh:274-294`). Separate observation from the action decision: applicability, resolved identity/path, ownership, version/artifact identity, configuration drift, and readiness. A small structured result with explicit error behavior would be less ambiguous than a single overloaded status line. Document stdout versus diagnostics, exit statuses, timeouts, and offline behavior; installers already use exit 2 for a successful skip (`lib/install.sh:827-852`).

   Side-effect freedom needs enforcement. Existing installers provision settings and plugins before returning “already installed” (`installers/install-claude.sh:54-59`, `installers/install-codex.sh:99-120`, `installers/install-pi.sh:76-84`). `--check` must branch before that work. Even version probes are not automatically read-only: `observed_component_version` explicitly avoids executing Azure CLI for that reason (`lib/install.sh:101-115`). Existing verify also launches login shells (`bin/verify:417-438`), which can execute user startup and direnv code.

   Shared checks alone do not produce an accurate dry-run. On a fresh install, configs gated on current tool presence are skipped even when the plan will install their owners (`setup.sh:499-501`). Git rendering depends on the installed Git version and nvim/delta availability (`lib/install.sh:582-599`). Planning must account for projected dependency state, report genuinely unknown results, and recheck immediately before mutation. Do not promise an exact plan solely because apply calls the same predicate.

5. **[P1] `versions.lock` needs an artifact model, not just centralized version strings.** Proposal lines 216–228 and 325–330 do not define the new schema or how existing consumers migrate. Today eget still obtains tags from `eget.toml` and requires a matching lock tag (`lib/install.sh:975-981`, `:1013-1020`). Leaving tags there while adding registry `pin` values and a new lock creates competing authorities. Choose one authoritative source and generate or validate all derived representations.

   Release tag, CLI-reported version, package version, source revision, archive digest, and installed binary digest are different identities. The proposal's own sd example says release 1.1.0 reports 1.0.0; literal “installed version = pin” would reject the correctly installed artifact. Existing eget state stores the extracted binary hash, while `eget.lock` stores the downloaded archive hash (`lib/install.sh:994-1003`, `:1036`, `:1072-1074`). A locally built tmux binary cannot be compared directly with its source archive digest. Plugin commits require a revision check rather than a CLI version probe.

   Define component keys, architecture normalization (`aarch64`, `arm64`, and `amd64` already occur), per-platform artifacts, exact apt package versions, companion identities, schema validation, missing/duplicate-row errors, and upgrade/downgrade verification. sbx currently requests `VERSION-*` and holds the package (`installers/install-sbx.sh:37-44`); matching an upstream release alone does not select an exact distro package revision. Its downgrade path and interaction with administrator holds need an explicit policy.

   A pin is also not a checksum. The eget bootstrap currently downloads a versioned archive without a digest verification (`installers/install-eget.sh:42-49`), and nvm's bootstrap script is fetched from a versioned URL without one (`installers/install-nvm.sh:49-64`). Centralizing these strings does not fix that trust gap. Preserve the bash tier's bootstrap requirements when selecting a lock parser; Python is not currently a prerequisite for that tier (`setup.sh:411-420`).

6. **[P1] Update policy must remain separate from ownership, backend, and configuration repair.** `converge`/`present`/`vendor` can describe version behavior, but cannot replace the existing installation/update contracts. sbx is apt-backed and pinned; xrdp is apt-backed and needs configuration/service reconciliation; OpenCode has a V1-to-V2 migration with service shutdown and rollback (`installers/install-opencode.sh:56-80`). “Vendor” does not itself establish which installation is safe to update.

   Specify that foreign installations can satisfy an accepted selection without being adopted or upgraded. Otherwise verify can fail forever on a foreign version that apply deliberately preserves. Do not infer ownership merely from a local prefix or package presence. Preserve component-specific force behavior: Codex and OpenCode refuse external installations even with `--force` (`installers/install-codex.sh:103-111`, `installers/install-opencode.sh:20-25`). The proposal's broad statement that force permits replacing anything not installed by setup is not today's contract.

   Do not let a binary-only `current` result suppress configuration repair. Today a working CLI can still receive settings or badge registration during its installer. After extracting those actions, make them independently selectable/checkable, including for intentionally external CLIs. Merely rewiring the badge into tmux does not update the application's cached plugin. `ai-config --check --plugins` validates enabled cache contents but does not install or update the plugin (`lib/ai_preferences.py:132-154`, `:184-185`).

7. **[P1] The clean-login-shell refresh can overwrite legitimate machine configuration and execute unrelated code.** Proposal lines 265–269 propose `env -i HOME=... bash -lc 'env -0'` as the base environment. This drops intentional inherited values, including custom XDG roots, EDITOR, PROJECTS_DIRS, and WSL/session context. Several are explicitly user-overridable in `entry/profile.sh:46-51` and `shell/env.sh:50-73`, `:86-87`, `:93-105`. Publishing defaults from the clean environment would change the meaning of those overrides and can make refresh use different state/config directories from apply.

   A login shell also runs system and user startup, and the profile runs direnv for its CWD (`entry/profile.sh:76-77`, `shell/env-runtime.sh:70-75`). A caller inside a project can therefore compute a project-specific environment or execute project hooks during a supposed base check. `env -i` is an environment reset, not a side-effect boundary.

   Define a bounded environment producer that avoids arbitrary login startup and project activation. Specify each managed variable's ownership and merge rule, preserve machine overrides and transport variables, and track previously managed PATH entries so removal is meaningful. Clearing the guards by itself cannot remove stale PATH segments or recompute `${VAR:-default}` exports from an inherited value.

8. **[P1] Global tmux environment changes do not establish freshness for every session or server.** Proposal lines 267 and 303–305 modify only the global environment and claim guards can then never be inherited. tmux merges global and session environments, with session values winning. Session overrides can therefore mask refreshed globals; custom `update-environment` settings can reintroduce them on attach. A removed global variable can also remain in a session. These are documented tmux semantics: [tmux manual, global and session environment](https://man.openbsd.org/tmux#GLOBAL_AND_SESSION_ENVIRONMENT).

   Scope refresh to a documented socket/server, inspect relevant sessions, and distinguish dotfiles-owned values from intentional session overrides. Define behavior outside tmux, with named/nested servers, and with no running server. The existing theme helper already has its own `DOTFILES_TMUX_SERVER` routing (`bin/theme-switcher:38-46`); all refresh operations must agree on the target.

   Reloading a config is not a complete reconciliation of running tmux state. Removed bindings and hooks remain unless explicitly unset; the current config already has deliberate cleanup for retired bindings and appended lists (`configs/tmux.conf:16-20`, `:96-100`, `:130-141`). Nor does replacing the tmux executable update the server process. Compare the server's `#{version}` with the installed client and report a server restart requirement; the manual identifies that format as the server version. A new client may also encounter an older server/protocol before config refresh can succeed. Do not claim that sourcing config brings the running server binary to its pin.

9. **[P1] Staleness must persist beyond a single refresh and identify a process, not just a pane.** Proposal lines 273–279 only report programs when a config changed “in this refresh.” If apply already copied that config, refresh may see no change at all. After one warning, a second refresh could say “everything current” while the old process still runs. Binary upgrades can require a restart without any config change. Symlinked sources also change at pull time, before refresh has a previous-content snapshot.

   Record the desired digest and the last acknowledged/observed process state across runs; include executable changes and all relevant config inputs. A pane option is shared mutable state: a nested shell can overwrite the outer shell's digest, and the outer shell may later resume stale. Use process identity/start identity where supported and report unknown coverage honestly. Shells outside tmux and OpenCode's shared service also need an explicit coverage decision.

   `reload` does not guarantee a clean shell even after all guards are cleared. Its comment explicitly says removed aliases/functions persist (`shell/tools/general.sh:133-140`), and conditional environment defaults retain inherited values. Do not stamp a fully current digest after a reload that leaves those changes unapplied. Distinguish re-sourced from restarted, or implement tracked removal for definitions and environment values that dotfiles owns. Digest inputs should also account for relevant local config and generated integrations, rather than only `entry/` and `shell/`.

10. **[P1] “Verify passes” cannot mean “apply has nothing to do” for the proposed whole-machine report.** Proposal lines 185–197 combine convergence checks with checkout state, upstream availability, enrollment, KVM/group readiness, and stale running processes. Apply cannot fix a dirty checkout, an unaccepted upstream release, BIOS virtualization, missing authentication, or an existing shell's environment.

    Existing behavior makes this concrete: setup can successfully install Tailscale without enrolling it (`installers/install-tailscale.sh:73-79`), while verification treats missing enrollment as a failure (`lib/work-host.sh:232-237`). Work setup warns about KVM or pending group access; work verification fails those conditions (`lib/install.sh:1342-1356`, `lib/work-host.sh:152-175`). An update can thus apply successfully and still exit unsuccessfully without having more automatic work available.

    Define separate convergence, health/readiness, and advisory outcomes with explicit exit rules. Pin drift is a convergence failure for an owned exact-pin component; newer upstream versions are normally advisory until accepted. Preserve work/Tailscale checks as health sections instead of silently dropping them from the new table. Preserve the existing mutation boundary around `--smoke`, which creates a sandbox (`bin/verify:300-307`), rather than folding it into read-only verify.

    Wrapping today's checkers is insufficient: `diff-config` prints drift but ordinarily exits successfully (`bin/diff-config:65-68`, `:149-157`), and verify treats several divergent configs as warnings (`bin/verify:108-119`). Normalize outcomes deliberately; do not infer health from wrapper exit status or parse presentation text as a durable interface.

11. **[P1] Config retirement needs exact ownership, merge semantics, and partial-failure behavior.** Proposal lines 245–258 add a useful deployment inventory, but “still points into the checkout” is weaker than “still has the link we deployed.” A user could redirect a previously managed link to a different file inside the same checkout and have it deleted. Compare the exact recorded link identity, without requiring its old source to still exist. For generated regular files, compare recorded content identity; for directory links, unlink the link rather than traversing/deleting its contents.

    Existing setup records a config ledger row after any successful `process_symlink`, even when the link was already current (`setup.sh:537-538`). Do not automatically treat those historical rows as proof that setup created the link. Validate retirement paths against approved roots and preserve the existing protection for custom XDG roots (`lib/install.sh:457-485`). A damaged or edited manifest must not authorize arbitrary removal merely because a digest matches.

    Preserve per-entry successful deployment state across partial failures. Replacing the entire manifest after a failed apply can forget items that still need retirement or falsely record writes that never occurred. Selection changes, unavailable owners, `--only`, and `--no-git` must not masquerade as source-file removal. Hooks and system files also have different ownership, privilege, and backup requirements; `deployed.tsv` alone does not reconcile those differences.

    AI key retirement needs a recursive three-way comparison: last applied overlay, current target, and new overlay. Record leaf paths, values and types; define lists and empty-container cleanup. The current merge overwrites scalar/list values as well as adding keys (`lib/config_files.py:33-42`), so “only adds keys” is inaccurate. Define whether active overlay keys still override user edits, and retain edited retired keys without subsequently forgetting the conflict. Preserve explicit exceptions such as Pi's user-owned, seed-once settings (`installers/install-pi.sh:28-45`).

12. **[P2] `--upgrade` needs real actions, complete package coverage, and explicit boundaries.** Proposal lines 226–228 and 317–318 say to invoke vendor installers through `run_installer`, but normal reruns of Rust, Pi, AWS, Claude, and Codex can exit without upgrading. `run_installer` only accepts a component name and forwards the global force bit (`lib/install.sh:828-848`). Implement dedicated update actions or an explicit operation argument; do not globally force every selected component just to update one vendor tool. Record outcomes from `rustup update` and `pi update` as well as installer outcomes.

    `apt-get install --only-upgrade PKG` for registered tools misses most dev/work prerequisites: Git, build tools, locales, Python packages, graphviz, and others have no component rows (`lib/config.sh:82-90`, `lib/install.sh:1404`). Docker is a package set, not just docker-ce (`lib/config.sh:88`), and xrdp includes a desktop/backend package set. Define whether upgrade covers those sets, how candidate indexes are refreshed, how holds are reported, and which installed-but-unselected or foreign components are eligible. “Every installed component” can exceed the saved selection and ownership boundary.

    Node and npm have no explicit policy in the proposal, despite Pi depending on Node. Updating nvm currently also invokes latest-LTS Node installation and npm@latest (`installers/install-nvm.sh:83-102`). Making nvm converge by routing through this whole path could silently upgrade Node/npm during plain update, contradicting the claim that unreviewed moving versions require `--upgrade`. Split manager convergence from runtime selection/update and preservation of project-specific Node versions.

The phase order should change before work begins:

1. **Phase 0: bounded fixes and contract decisions.** Fix guard/reload defects with honest remaining limitations; fix ledger parsing and apt-skip ownership; guard Docker service work; audit conditional-context error propagation. Preserve journals until recovery succeeds. Make the work-tier compatibility decision and update setup plus verification together: skipping sbx alone is insufficient because `bin/verify:277-289` still requires work-host checks for `--tier work`, and `install_work_packages` still configures KVM/builders (`lib/install.sh:1406-1409`).
2. **Phase 1: profile and observation.** Define profile merge/replacement/migration, per-tool selections, exclusions, version identities, ownership, dependency resolution, and check results. Add read-only convergence checks and retain health as a separate outcome. Establish regression coverage for individual AI flags, external tools, unsupported platforms, custom XDG roots, moved/downgraded pins, and partial failures before switching dispatch.
3. **Phase 2: apply, lock migration, and config state.** Move pins with all consumers, implement checks and targeted operations, and make dry-run use projected state. Establish deployment/retirement state and move config/plugin repair out of binary-installer early-exit paths. Preserve previous successful state on partial failure. Keep editor-plugin installation explicitly opt-in unless the profile deliberately enrolls it: today `bin/install-editor-plugins` is a separate action, and no setup phase calls it. Phase 0's PlugUpdate change alone would not make update manage those plugins.
4. **Phase 3: refresh and update orchestration.** Add a controlled environment producer, tmux scope/version checks, persistent process staleness, and then pull/re-exec/apply/upgrade/refresh/verify. Serialize the whole operation, including the Git transition, and carry a run identifier/lock through re-exec. Existing state locks protect individual writes, not an entire update. Specify failure/exit behavior after partial success, profile migration under new code, no-upstream/detached/worktree cases, and ahead-only branches. Refresh should be invoked once: the proposal currently says both that apply includes it (line 263) and that update calls it again (line 319).
5. **Phase 4: maintenance automation.** Add bump/CI once lock validation and all pinned consumers agree. Define how commit-pinned plugins participate in “latest” and the 14-day cooldown, and preserve multi-architecture checks before writing a new lock.

If an earlier front door is useful, it can wrap existing behavior with explicitly limited guarantees. It should not claim “eleven steps into one,” whole-machine convergence, persistent restart reporting, or exact dry-run results before the corresponding contracts exist. Pulling the live symlinked checkout already exposes new files to new processes before apply finishes; re-exec avoids mixed old/new script execution but does not provide rollback for the machine. Report the checked-out revision, completed actions, remaining drift, and unresolved recovery state accordingly.
