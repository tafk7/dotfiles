# sbx kits

Docker Sandboxes (sbx) v3 kits that belong to no project: coding-agent
harnesses, model-gateway access, the portable part of this repository's AI
configuration. Layer them onto any workload, such as
FINN's (`finn.yaml` in a FINN checkout). Validated with the sbx version
`lib/config.sh` pins (`SBX_VERSION`).

| Kit | Kind | Adds |
|---|---|---|
| `harness/claude` | mixin | Claude Code (pinned native binary), its network rules and Anthropic credential request, session volumes; Claude reads the composed agent instructions |
| `harness/codex` | mixin | Codex CLI (pinned native binary), its network rules and OpenAI credential request |
| `auth/llm-gateway` | mixin | Claude Code and Codex through an API gateway that takes a key header; network access to that host only |
| `ai-preferences` | mixin | `configs/claude-settings.json`'s portable keys (as Claude Code managed settings), keybindings, and the skills that need nothing from the host; generated by `sync-portable.py` |

The harness kits are Docker's sandbox-kit-spec examples, adapted for sbx 0.46.0
(see each file's header). Each is a binary in a `scratch` layer, fetched when
the kit is built, so a sandbox needs no download at start.

## Use

```bash
sbx create --name work \
    --kit "$DOTFILES_DIR/kits/harness/claude" \
    --kit "$DOTFILES_DIR/kits/ai-preferences" \
    WORKLOAD_KIT WORKSPACE …
sbx exec -it work claude
```

A kit is named after its directory and referenced by absolute path. Building a
kit from source needs BuildKit's OCI exporter: Docker's containerd image store,
or `BUILDX_BUILDER=sbx-kits`, the `docker-container` builder `./setup.sh --work`
creates (with buildkitd settings, such as a site's DNS servers, from the
untracked `~/.config/dotfiles/buildkitd-sbx-kits.toml`).

## Portable preferences

`ai-preferences` is generated from `configs/`; edit those, then run
`kits/sync-portable.py` (the pre-commit hook and the test suite run it with
`--check`). It carries no credentials and selects no model or provider: the
model belongs to whatever serves requests (a gateway names its own), the status
line needs a host script, and the viz skill the host's VS Code window. Claude
Code reads the settings as managed settings, so the harness kit's own
`settings.json` (auth mode, bypass permissions) stays the harness's.

## Credentials

Nothing here holds a secret. A harness's own credential is sbx's
(`sbx secret set anthropic` / `openai`, approved when a kit first asks).

A gateway uses a host-side **custom secret**: sbx gives the sandbox a
placeholder and replaces it in requests to the gateway host. Register it as a
command that reads the key where it already lives, so a new key needs no new
registration, and keep the kit's arguments in a file:

```bash
sbx secret set-custom --host llm-api.example.com --env LLM_GATEWAY_KEY \
    --command 'cat /home/you/.config/llm-gateway/key'
cat > ~/.config/llm-gateway/gateway.args <<'EOF'
host=llm-api.example.com
header=Ocp-Apim-Subscription-Key
anthropic_base_url=https://llm-api.example.com/…
EOF
sbx create … --kit "$DOTFILES_DIR/kits/auth/llm-gateway" \
    --kit-args-file ~/.config/llm-gateway/gateway.args …
```

Claude Code sends the header from `ANTHROPIC_CUSTOM_HEADERS` (set in Bash);
Codex gets a model provider with `env_http_headers` from `openai_base_url`.
Codex through a real gateway is not yet verified.
